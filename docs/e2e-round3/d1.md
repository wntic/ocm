# D3 — Concurrency and interruption

## D3.1 — two concurrent `ocm update` (same home, pending upstream changes)

Own source copies (`d1-alpha-src`, `d1-exec-src`, empty commits as pending
upstream changes). H=`home-d1-d31`, `greet-kit` installed.

```
$ ( HOME=$H ocm update >upd1.out 2>upd1.err; ) & ( HOME=$H ocm update >upd2.out 2>upd2.err; ) & wait
upd1 exit=0
  updating ocm-e2e3-alpha...
    935ec7e → c14eb04
  updating ocm-e2e3-exec...
    4e0c2f8 → ce2cd7e
upd2 exit=1
  updating ocm-e2e3-alpha...
  updating ocm-e2e3-exec...
    4e0c2f8 → ce2cd7e
--stderr (upd2)--
  failed: cannot access file:///tmp/ocm-e2e3/d1-alpha-src — the repository is private, unreachable, or the URL is wrong
  update failed for 1 marketplace(s): ocm-e2e3-alpha
```

Repeated 3 more rounds: deterministic — exactly one process wins, the loser
fails on the first marketplace it tries to pull concurrently, exit 1,
per-marketplace failure summary, the other marketplace still updated
(multi-item rule held).

Registry after every round: parses (jq OK), both marketplace records and
`lastSync` intact, links intact, `ocm doctor` exit 0. **No corruption.**

Root cause of the loser's error (traced): the two updates `git fetch` the
same cache clone; git fails with
`error: cannot lock ref 'refs/remotes/origin/main': is at … but expected …`
and `pullRepo` (loader/sync.js:24-29) maps ANY failed fetch to
"cannot access ${url} — the repository is private, unreachable, or the URL
is wrong". The loser fails *cleanly* but the diagnosis is wrong — nothing is
wrong with the URL or the repo's privacy; another ocm process holds the
clone. See finding D3-1.

**Verdict D3.1: pass with defect** (clean failure, no corruption; misleading
error message).

## D3.2 — `ocm add` while opencode's loader sync runs

First attempt (TUI under expect, `OCM_SYNC_INTERVAL_MS=0`, neutral cwd —
note: my first run accidentally used the repo cwd and was discarded and
redone from `$H`), firing `ocm add` (big-src) + `ocm update` + `ocm install`
concurrently with the TUI's startup sync:

```
add exit=0      cloned … added marketplace "ocm-e2e3-big" (big-01…big-10)
update exit=0   updating ocm-e2e3-alpha... e350fcb → 24acec9 …
install exit=0  already installed greet-kit@ocm-e2e3-alpha
tui exit=0
registry afterwards: [ "ocm-e2e3-alpha", "ocm-e2e3-exec" ]   ← ocm-e2e3-big GONE
```

**Silent data loss**: `ocm add` printed full success (exit 0) yet the
marketplace record is absent from the registry afterwards. The cache clone
(`~/.cache/ocm/marketplaces/ocm-e2e3-big/`) and links dir remain as orphans.

Isolation:

- **add vs loader sync alone** (no CLI update; 3 attempts, TUI with
  `OCM_SYNC_INTERVAL_MS=0`): survived 3/3 — registry kept both marketplaces,
  parses OK. The loader's write paths (`recordSync`, `refreshRecords` in
  loader/sync.js) re-read the raw file immediately before an atomic rename,
  so its race window is small; not lost in 3 attempts.
- **add vs CLI update alone** (no TUI, `home-d1-d32b`): reproduced
  immediately —

```
$ HOME=$H2 ocm add file:///tmp/ocm-e2e3/repos/big-src & HOME=$H2 ocm update </dev/null & wait
add out:  cloning … added marketplace "ocm-e2e3-big" …
upd out:  updating ocm-e2e3-alpha... 24acec9 → c2c0644 …
registry afterwards: [ "ocm-e2e3-alpha" ]        ← ocm-e2e3-big LOST
```

Mechanism: `ocm update` loads the registry at command start (before the
add's save), spends the pull latency, then `saveRegistry(registry)` per
marketplace (src/commands/update.ts:121) — a classic unlocked
read-modify-write that overwrites the concurrently added record.

Aftermath for the user: `ocm list --all` shows no trace of the added
marketplace (the add said it succeeded); `ocm doctor` exit 1 with 11 errors:

```
  error   …/.cache/ocm/links/ocm-e2e3-big/skills/big-08--notes-08: no marketplace owns this link (orphaned by a loader uninstall?) — ocm doctor --fix removes it
  … (11 orphaned-link errors, same shape)
```

— a misleading diagnosis (nothing was uninstalled; a concurrent update
clobbered the record). `ocm doctor --fix` would delete the links, and the
orphaned cache clone is not reported at all. See finding D3-2 (high).

**Verdict D3.2: fail** — registry stays parseable, but the added marketplace
record is silently lost when add races any CLI read-modify-write (update;
by extension install/uninstall/remove). Add-vs-loader-sync specifically
survived 3/3 attempts.

## D3.3 — `kill -9` an `ocm install` mid-run

H=`home-d1-d33` (big marketplace, 10 plugins).

Round 1 — 15 kill attempts against `ocm install` at 5–50 ms delays
(uninstall/reinstall cycles): kills landed only during bun startup
(exit 137); every check: registry parses, no `registry.json.tmp` leftovers,
`ocm install` / `ocm doctor` afterwards clean (exit 0).

Round 2 — kill `ocm add` mid-clone (the long operation), delays 20–90 ms,
own copy of alpha/big sources, fresh-ish home `home-d1-d33c`:

```
delay=0.02s killed=yes exit=137 registry_keys=0 parses cache_clone=absent
delay=0.03s killed=no  exit=1   ← immediate next add FAILED:
  cloning file:///tmp/ocm-e2e3/repos/big-src...
  cannot access file:///tmp/ocm-e2e3/repos/big-src — the repository is private, unreachable, or the URL is wrong
```

Deterministic repro of the interruption aftermath:

```
$ HOME=$H ocm add file:///tmp/ocm-e2e3/repos/big-src & sleep 0.02; kill -9 %1
$ sleep 2                      # orphaned git clone finishes, leaves unregistered dir
$ HOME=$H ocm add file:///tmp/ocm-e2e3/repos/big-src
cloning file:///tmp/ocm-e2e3/repos/big-src...
cannot access file:///tmp/ocm-e2e3/repos/big-src — the repository is private, unreachable, or the URL is wrong
exit=1
$ HOME=$H ocm add file:///tmp/ocm-e2e3/repos/big-src     # second retry
cloning file:///tmp/ocm-e2e3/repos/big-src...
added marketplace "ocm-e2e3-big" …
exit=0
```

Mechanism (loader/source.js placeClone): clone goes directly into the final
cache dir; a SIGKILLed add runs no cleanup, and the orphaned `git clone`
child keeps writing. The retry's clone then hits git's "destination path
already exists" → mapped to the same misleading "cannot access" message;
that failed attempt's catch does `rmSync(dir)` (spec 05), so the *second*
retry succeeds. Registry was never half-written in ~35 kill scenarios — the
atomic-write claim (old-or-new, always parseable) held throughout; no
`registry.json.tmp` ever left behind. See finding D3-3.

**Verdict D3.3: pass on the atomic-write claim; defect on recovery UX**
(first retry after an interrupted add fails with a misleading network-flavoured
error; second retry succeeds).
