## Mechanism notes (for the defects below)

- The update restart notice fires iff `materialized.created > 0 ||
  materialized.removed > 0` (`src/commands/update-report.ts:135`).
- Command/agent links are symlinks: unchanged target → `"ok"`, never
  counted (`loader/links.js:63`).
- Skill mirrors are **rendered** files whose trailer embeds the marketplace
  revision (`<!-- ocm: rendered from … @ <rev> -->`). Every revision advance
  changes the trailer → rewrite → `"created"` (`loader/links.js:118-145`).

Consequence: with an installed skill present, *any* revision-advancing
update prints the restart notice (even when the skill body did not change —
verified: v4 round changed only `greeter.md`, the notice fired off the
farewell mirror's revision stamp). With **no** skills installed, a real
command/agent content change prints **no** notice (verified: uninstalled
new-kit, changed `greeter.md` v4→v5, full update, notice absent although
the on-disk agent content changed and the running session keeps the stale
version until restart).

## Defects

### A7-D1 — Unrelated mutations print zero blocked-trust lines; spec 23 §7 says one per run (area: CLI, severity: low)
Test:     A7.8 / F35
Command:  `env HOME=$H ocm install greet-kit` (home with trusted alpha + untrusted exec marketplaces)
Expected: plan A7.8 / spec 23 §7 — "one line per affected marketplace" on
          every mutation run (`2 components blocked pending trust — run ocm trust <mp>`)
Actual:   ```
          $ env HOME=$H ocm install greet-kit
          exit=0
          --stdout--
          installed greet-kit@ocm-e2e3-alpha (1 command, 1 agent, 1 skill)
          restart opencode to activate
          --stderr--
          (empty)
          ```
          Zero blocked lines. The line does print (once, correctly) on
          `ocm update`, which reconciles the affected marketplace
          (`reportMutationWarnings` is called with the mutation's own
          marketplace only — `src/commands/plugins.ts:27,37`).
Impact:   A user who declined trust gets no reminder on later installs that
          components sit blocked; they must run `ocm update` (or `ocm list`)
          to rediscover it. Direction is "too quiet", not noisy — the
          original F35 complaint — but it diverges from the spec'd
          once-per-run summary. (The phase test only covers the
          same-marketplace case, where the line does print.)

### A7-D2 — `ocm update <plugin>@<mp>` narrows the action, not just the report (area: CLI, severity: med)
Test:     A7.10 / F42
Command:  `env HOME=$H ocm update greet-kit@ocm-e2e3-alpha </dev/null` (upstream commit changing greet-kit AND new-kit)
Expected: spec 23 §8 — "same action as the marketplace-wide form today;
          only the report narrows"
Actual:   ```
          $ env HOME=$H ocm update greet-kit@ocm-e2e3-alpha
          exit=0
          --stdout--
          updating ocm-e2e3-alpha...
            e68daca → c4d6aab
            greet-kit
              ~ agents/greeter.md
          --stderr--
          (empty)
          ```
          The whole marketplace is pulled (revision e68daca → c4d6aab, both
          plugins' commits fetched) but only greet-kit is materialized:
          `agents/greet-kit:greeter.md` = "v3 greeter" while
          `links/…/new-kit--farewell/SKILL.md` stays "v2 farewell" until the
          next marketplace-wide update. Reproduced twice (v2 and v3 rounds),
          deterministic. Root: `materializeLinks(name, entry, false, plugin)`
          in `src/commands/update.ts:126`.
Impact:   After a scoped update the registry records the new revision while
          other plugins' installed mirrors are stale relative to it — the
          marketplace claims a state it does not have on disk. The stale
          content is applied silently by whichever full update comes later
          (or never).

### A7-D3 — Post-scoped-update `ocm update` prints "already up to date" and then a restart notice (area: CLI, severity: low)
Test:     A7.10 / F42 (consequence of A7-D2)
Command:  `env HOME=$H ocm update </dev/null` immediately after A7-D2's scoped update
Expected: a coherent report — "already up to date" means nothing happened
Actual:   ```
          $ env HOME=$H ocm update
          exit=0
          --stdout--
          updating ocm-e2e3-alpha...
            already up to date
            restart opencode to activate
          --stderr--
          (empty)
          ```
          (The notice is honest in substance — this run materialized the
          farewell change deferred by the scoped update — but paired with
          "already up to date" it reads as a contradiction.)
Impact:   User cannot tell what the restart is for; the two lines describe
          the same run in incompatible terms.

### A7-D4 — Restart notice coupled to skill-mirror revision stamps, not to actual changes (area: CLI/loader, severity: low)
Test:     A7.5 follow-up / F16, round-1 #3 (edge beyond the plan's cases)
Command:  `env HOME=$H ocm update </dev/null` with only `greet-kit` (command+agent, no skills) installed; upstream changed `agents/greeter.md`
Expected: spec 23 §5 rationale (U3.1): the running session keeps the stale
          command/agent until restart "and the report must say so"
Actual:   ```
          $ env HOME=$H ocm update
          exit=0
          --stdout--
          updating ocm-e2e3-alpha...
            343f9fe → 16ab2a0
            greet-kit
              ~ agents/greeter.md
          --stderr--
          (empty)
          ```
          No restart notice, though `agents/greet-kit:greeter.md` changed
          on disk (v4 → v5). Conversely, when a skill is installed, the
          notice fires on every revision advance even if the skill body did
          not change (the rendered mirror's `@ <rev>` trailer rewrites →
          counted as "created"). Spec §5's letter (created-or-removed) is
          met; its rationale is not, for skill-less plugins.
Impact:   Skill-less plugin users are never told to restart after content
          updates; skill users are told on every pull regardless of change.
          Both directions point at the same coupling.
