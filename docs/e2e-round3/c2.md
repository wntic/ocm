## C4.1 — grandfathered manifest-less plugin colliding with a new marketplace's plugin

renamed `legacy-tool` → `big-03` (command `old.md`) so the name collides with

*name* is the collision surface, spec 18).

## C4.2 — grandfathered plugin renamed upstream via `renames` map, no manifest

Two variants: local marketplace (assignment's ask) and git marketplace (to
answer "does this share A4-F3's root cause" by contrast).

### local variant (H=home-c2-02, own copy c2-legacy-mp2)

Grandfathered `legacy-tool` (add with authored manifest → delete file +
strip registry `manifest`), then upstream change = rename dir to
`legacy-tool-2` + `renames` map in marketplace.json:

```
$ env HOME=$H ocm update </dev/null
exit=0
--stdout--
updating legacy-mp...
  1 created, 1 removed, 0 skipped
  renamed legacy-tool → legacy-tool-2
  restart opencode to activate
--stderr--
```

**The rename applies.** Registry afterwards has exactly ONE record
(`legacy-tool-2`, `enabled: true`, `manifest: {}`) — not both ✓; link moved
(`legacy-tool-2:old.md`); doctor reports `legacy: "legacy-tool-2" has no
plugin.json …` (exit 0). No refusal, no warning that the rename changed a
grandfathered plugin. Second update: no-op beyond the header; plugin still
enabled and live. The report states the rename ✓ and the registry is
single-recorded ✓ — but the grandfather survived a plugin change, which
spec 19's edge-case table says should end it ("the grandfather ends when the
plugin changes").

### git variant (H=home-c2-03, own repo c2-legacy-git)

Commit A: `legacy-tool` + authored manifest → add. Commit B: manifest
removed; clone advanced to B and registry `revision` = B, record's manifest
stripped (a4's pre-spec simulation). No-op update at B..B: `already up to
date`, no warning — grandfather holds ✓. Commit C: `git mv
plugins/legacy-tool plugins/legacy-tool-2` + `renames` map in
marketplace.json (still no manifest). `git diff B..C` = `R100
plugins/legacy-tool/commands/old.md → plugins/legacy-tool-2/commands/old.md`
+ `M marketplace.json`.

```
$ env HOME=$H ocm update </dev/null
exit=0
--stdout--
updating legacy-git-mp...
  bf97174 → 938fc22
  renamed legacy-tool → legacy-tool-2
  restart opencode to activate
--stderr--
  warning: plugin "legacy-tool-2": plugins/legacy-tool-2/plugin.json is missing — not installed; add one ({ "description": "…" }) and update again
```

**The rename is refused** — spec 19 rule 3: the rename counts as a change,
the grandfather ends, the plugin is not installed. Registry: `plugins: {}`
(the record was migrated by the renames pass, then dropped by the manifest
refusal) — not both records ✓; the `legacy-tool:old.md` link came down;
doctor is silent (no legacy warning — nothing registered). `ocm list --all`
shows `legacy-git-mp` with zero plugins.

So: local = rename applies + grandfather survives; git = rename refused +
grandfather ends. Same plugin, same upstream change, opposite outcomes —
and the difference is exactly A4-F3's root cause (`pluginFileChanges`
derives the `changed` set only from a git revision pair; a local
marketplace has no revision pair, so `changed` is always empty and the
grandfather-end condition never fires). **The rename variant shares the
A4-F3 root cause — confirmed by direct contrast.**

Two reporting defects on the git variant:

1. stdout says `renamed legacy-tool → legacy-tool-2` — an event that did
   not survive the update — while the actual outcome (record dropped,
   plugin uninstalled, link removed) is stated nowhere as such. A user
   reading the report concludes their plugin moved to `legacy-tool-2` and
   kept working; in fact it is gone from the registry entirely.
2. Same refusal text as A4-F4: no why-now (the plugin was grandfathered;
   the rename ended it), no removal line.

**Verdict C4.2: partial.** The report states which outcome occurred on
each path and neither registry ends with both records ✓; but the two paths
disagree about whether a rename ends the grandfather (local defect = A4-F3
variant), and the git-path report pairs a `renamed` line with a refusal
whose net effect (plugin gone) is never stated.

(Methodology note: one setup command accidentally ran `git commit` inside
the ocm repo because a `cd` did not take effect; the commit was undone
immediately with `git reset HEAD~1`, the stray file removed, and `git
status` verified back to its prior state — only untracked docs/e2e-round3
files, HEAD at `4eb4df0`. No repo content was changed.)

### C4 cross-cutting invariants (homes c2-01, c2-02, c2-03)

1. No `$H/.claude`, no `$H/.agents` in any home — clean.
2. `plugins/` contains only `ocm-loader.js` in every home.
3. No broken symlinks under `commands/`, `agents/`, `plugins/`.
4. `tui.json` parses everywhere. `opencode.json` is absent in c2-02/c2-03
   (no skills shipped — ocm never wrote it; not a violation, same as a4).
5. `ocm doctor` exit 0 in all three homes in their final states.

## Findings index (c2)

- C4-F1 — local marketplaces: a `renames`-map rename of a grandfathered
  manifest-less plugin applies silently; the grandfather does not end
  (med; A4-F3 variant, same root cause — verified by local/git contrast)

  MCP key changes never gate the restart line (low)

Observations (not filed as defects):

- Non-TTY `ocm update` with pending trust prints the prompt question to
  stderr and silently skips (records nothing); `ocm trust` under the same
  conditions prints a "stdin is not interactive — re-run with --yes" hint
  and exits 1 (spec 16 §2). The update path has no such hint. Safe (the
  component stays blocked) but inconsistent.
- `ocm trust <mp> --yes` grants without printing the component listing
  (`add --trust` prints it, F58). Spec 16 §2 says "--yes grants exactly as
  an interactive `y`", which an interactive `y` precedes with the listing;
  b2/B3.3 passed this as-is, so recorded here as an observation only.
- Colour appears only on TTY; all non-TTY captures are clean. Data on
  stdout, warnings/errors on stderr, exit codes 0/1 observed correctly
  throughout. No stack traces, raw node errors, or debug JSON anywhere.
- User-key survival was not exercised (no user keys seeded in the c2
  homes); configs parse and doctor agrees everywhere.
