# B1 — Upgrade in place (0.5.1 → 0.6.0)

ocm: 0.5.1 and 0.6.0 (published npm bits at the isolated prefixes in SHARED.md)
opencode: 1.18.31 (`/Users/yegorvorobyev/.opencode/bin/opencode`)
Homes: `/tmp/ocm-e2e4/home-b1-{a,b,c}`, work under `/tmp/ocm-e2e4/work-b1/`.

**Method note (required by the plan):** "switching installed version" below means
switching which prefix's binary is invoked (`v051/...bin/ocm` ↔ `v060/...bin/ocm`).
This is equivalent to `npm i -g @wntic/ocm@0.5.1` / `@0.6.0` for everything ocm
does (the binary, the loader modules it copies, and the version stamp it writes),
while leaving the user's real global ocm (a repo symlink) untouched. `ocm --version`
was confirmed before every scenario: 0.5.1 before each install phase, 0.6.0 before
each upgrade phase (recorded in the transcripts below).

Fixture copies: `exec-mp` and `local-mp` were `cp -R`'d to `work-b1/` before use;
the shared fixtures were not mutated. `opencode debug config` and all TUI sessions
ran from a neutral cwd (`work-b1/cwd`) — running from the repo dir leaks the repo's
own project config into `debug config` and was avoided after the first attempt.

## Judgment — is the user told, and is the remedy actionable?

**Scenario A (same root):** the user is told **nothing** by the first command.
The only signal is doctor's 34 stale-loader errors, which do name an actionable
remedy (`ocm init` / `ocm update`) that verifiably works. Verdict: recoverable,
but "upgrade in place → doctor clean" (the plan's promise) is false, and the
user who never runs doctor notices nothing while running 0.5.1 loader code
(including the pre-0.6.0 hardcoded config root and none of 0.6.0's loader fixes)
under a 0.6.0 CLI. F166.

**Scenarios B/C (root moves):** doctor's message is excellent — verbatim what
brief 28 §2.2 specifies, states both roots, which one opencode reads, and a
direction-aware remedy a user can act on without reading source ("unset
XDG_CONFIG_HOME…" / "set XDG_CONFIG_HOME to <dir>…", both verified to work).
The mutating-command warning (§2.3) also fires as specified. The gap is the
first-command experience: `list`/`search`/`info` flatly deny the install exists
with no hint (F167), and the "re-add here" remedy walks the user into doctor
errors that mislabel the other root's mirrors as orphans and a `--fix` that
deletes them (F168).

## Findings

## F166 — upgrade in place (0.5.1 → 0.6.0) leaves the loader stale; first command silent; doctor exits 1   (area: CLI, severity: med)

Test:        B1 / steps 2–3 (scenario A)
ocm version: 0.5.1 → 0.6.0      opencode: 1.18.31
XDG:         unset
Command:     `HOME=$H <v051>/ocm add …` ×3, `ocm trust … --yes` ×2 (0.5.1); then `HOME=$H <v060>/ocm list --all`, `ocm doctor`
Expected:    round-4 plan B1 step 3: "First command → migration output, no losses. `ocm doctor` clean." After `npm i -g @wntic/ocm@0.6.0` the installation should be healthy without a repair step.
Actual:      `ocm list --all` → exit 0, correct data, **zero output about the loader**. `ocm doctor` → exit 1, `34 errors, 0 warnings`: `atomic.js: not installed (ocm init)`, `lock.js/manifest-gate.js/mcp-line.js: not installed`, and 30 × `stale version comment — a stale core silently no-ops (ocm update)`. Installed modules are stamped `// ocm-version: 0.5.1 …`; the 0.6.0-only loader modules are absent. `ocm update` (exit 0) refreshes all modules to `// ocm-version: 0.6.0 …`; doctor then exits 0.
Impact:      a user who upgrades the CLI keeps executing 0.5.1 loader code (hardcoded config root, none of 0.6.0's loader fixes — lock, manifest gate, mcp-line) at every opencode start until they happen to run a mutating command or doctor. Nothing breaks and the remedy works, but "upgrade" silently half-applies, and the plan's doctor-clean promise fails.
Regression?: new defect — round 3 tested only the downgrade direction (F118, 0.2.0 binary over a 0.5 home, 23 stale-core errors); the published-0.5.1 → published-0.6.0 upgrade path was not exercised in round 3.

## F167 — read-only commands deny a stranded install exists, with no hint   (area: CLI, severity: med)

Test:        B1 / steps 3–5 (scenarios B and C, first 0.6.0 command with XDG set)
ocm version: 0.6.0      opencode: 1.18.31
XDG:         set to /tmp/ocm-e2e4/work-b1/xdg-{b,c} (install lives in the default root, 3 marketplaces, trusted)
Command:     `HOME=$H XDG_CONFIG_HOME=$X ocm list --all`; also `ocm search hello`, `ocm info exec-kit`
Expected:    brief 28 §2.2 fixed the "most misleading sentence ocm can produce in this state" for doctor; the same state reached through any other command should not reintroduce it. The plan expects the user to be told what happened.
Actual:      `ocm list --all` → stdout `no marketplaces added yet (ocm add <url|path>)`, stderr empty, exit 0. `ocm search hello` → stderr `no matches for "hello"`, exit 1. `ocm info exec-kit` → stderr `plugin "exec-kit" not found in any marketplace (ocm search <query>, or ocm update)`, exit 1. No command mentions the stranded install; only `doctor` and mutating commands do.
Impact:      the first command a user runs after upgrading (`list`) tells them their three marketplaces do not exist and suggests `ocm add` — the exact "complete, successful-looking" false state F65/brief 28 set out to kill, now one command away from the good doctor message. A user who trusts `list` re-adds marketplaces and creates a second install.
Regression?: new defect (residue of the F65 fix). F65 itself behaved as described in round 3 and its doctor/mutating-notice fix works verbatim; the read-only surface was not covered.

## F168 — `ocm doctor --fix` under one config root deletes the other root's skill mirrors (shared cache, per-root registry) and prints a fix that did not happen   (area: CLI, severity: med)

Test:        B1 / step 5 (scenario C: re-add under XDG, then `ocm doctor --fix`)
ocm version: 0.6.0      opencode: 1.18.31
XDG:         set to /tmp/ocm-e2e4/work-b1/xdg-c; default root holds the original 3-marketplace install, XDG root holds a re-added exec-mp
Command:     `HOME=$H XDG_CONFIG_HOME=$X ocm add …/exec-mp` (the stranded message's own remedy), then `HOME=$H XDG_CONFIG_HOME=$X ocm doctor --fix`
Expected:    brief 28 §1 keeps `~/.cache/ocm` anchored to `$HOME` precisely because it is shared; a fix run against one root must not destroy state belonging to a registry it cannot see. Doctor's claims must be true facts.
Actual:      doctor reports the old root's mirrors as `no marketplace owns this link (orphaned by a loader uninstall?) — ocm doctor --fix removes it` (3 errors). `--fix` prints `fixed …/hello-kit--hello-guide: removed`, `fixed …/demo-kit--code-review: removed`, `fixed …/release-kit--release-notes: removed`, plus two `fixed …: removed from skills.paths` lines — while no `opencode.json` exists in the XDG root at all (`setSkillsPath` no-ops on a missing file, `loader/config.js:27`; the "fixed" line is unconditional, `src/commands/doctor-orphans.ts:90`). Both skills dirs under `~/.cache/ocm/links/` are gone; the old root's `opencode.json` still lists both `skills.paths`, so that root's opencode silently loses its skills. `ocm update` in the old root recovers (`2 created, 0 removed, 0 skipped`).
Impact:      a user who follows the stranded message's "re-add those marketplaces here" remedy, then obeys doctor's own `--fix` suggestion, silently degrades the install they were told to keep as an alternative. Recoverable, but the destruction is cross-root, unexplained, and the report contains false "fixed" claims.
Regression?: new defect — dual-root states cannot arise before 0.6.0 (0.5.x ignores XDG entirely); no round-3 counterpart.
