### Step 12 — background `ocm update` racing a TUI session — PASS (20/20)

Script `work-b35/step12.sh`, log `step12.log`. Twenty pairs of a background
`ocm update` and an expect TUI session on `home-b35-12`, alternating which side
starts first, every third pair with `SLOW_GIT_SECS=3` on the update. After every

silently when the lock is held. The next TUI start after the hold synced
normally. `ocm list` / `ocm doctor` exit 0 afterwards.

### Step 13 — TUI mutation while the same process holds the lock in startup sync — PASS

### Step 14 — SIGINT to the lock holder — PASS

Script `work-b35/step14c.py` (python `subprocess`, because a bash background job

- `kill -INT` kills the holder immediately: returncode −2 (killed by SIGINT;

- The lock file is left behind as a corpse — expected: SIGINT is the default

- The **next mutation is not blocked**: it starts in 0.04 s, breaks the corpse
  on its first poll with exactly one stderr warning —
  `warning: removed a stale ocm lock (pid 12128, 0m old) — a previous ocm was killed`

### Step 15 — kill −9 with a waiter; live-pid stub ceiling — PASS

Script `work-b35/step15.py`.

### Step 21 — upstream fixes the broken shape; update with stdin closed — PASS

`old-server` was fixed in the copy to the valid shape

- The change is detected and attributed precisely:
  `marketplace "old-mp" shipped code that changed since you trusted it:`

- With stdin at EOF the prompt does **not hang**: it defaults to N and warns

- **`good-server` is not re-prompted** — only `old-server` is listed as

  untouched by the update.

Then `ocm trust old-mp --yes` (exit 0) installs both: opencode.json now
carries `ocm--legacy-mcp--good-server` and `ocm--legacy-mcp--old-server`, both
in the normalised shape.

## Findings

## F206 — `/ocm` TUI dialog freezes opencode entirely (100% CPU, unkillable except kill −9) when the terminal reports 0 columns/rows — infinite loop in `wrapText` via `dialogSize`   (area: loader/TUI, severity: high)

**Test:** B3 step 13 setup — drive `/ocm` in the opencode TUI under expect.
**Command:** `spawn opencode` (expect's default pty: `isTTY` true, but
`process.stdout.columns`/`rows` are 0), then send `/ocm\r`.
**Expected:** the dialog renders (or degrades); the session stays responsive.
**Actual:** opencode freezes at 100% CPU before any dialog pixels appear; ctrl-c
does nothing; only `kill -9` ends it. No output, no error — it looks exactly
like the "hung test" trap AGENTS.md warns about.
**Root cause (bisected, `work-b35/probe*.log` + `fit-test.mjs`):**
`loader/ui-dialog.js` `fit()` → `dialogSize` computes `frame = min(bucket,
width - 2)` = `min(bucket, -2)` = −2 at columns 0, then `wrapText(line, -11)`
runs `while (rest.length > width)` with a negative width — `rest` never
shrinks, infinite loop. Probe chain: dialog API calls succeed on 1.18.31
(probe-tui); the hang reproduces without ocm's UI code (probe2–4 bisect it into
`fit()`); probe5 prints `columns=0 rows=0`; a standalone `bun fit-test.mjs`
with the same code and a real width is fine; probe6 shows the same expect
drive works perfectly once the pty is sized (`stty rows 30 cols 100` before
`exec opencode`).
**Impact:** any embedder that allocates a pty without a size (CI harnesses,
expect scripts, some terminal multiplexers during resize) hits a hard
freeze of the whole opencode process, not just the dialog. Real terminals at
normal sizes are unaffected — every other TUI scenario in this round passed.
**Fix sketch:** clamp the computed frame to a minimum (e.g. `max(frame, 20)`)
or bail out of `dialogSize`/`wrapText` when `width < 2`; `wrapText` should
also treat `width <= 0` as "return the line unwrapped" rather than loop.
**Regression?:** new defect, found by round 4 (round 3 drove `/ocm` only in
sized terminals, or not via a 0×0 pty). Not introduced by the lock work — it
is in the dialog sizing shipped with the `/ocm` UI.

No other new findings: steps 12–16 and 20–22 all pass against the published
0.6.0 binary, and every refusal/warning matches brief 27/34's specified text
and timing (10 s ceiling timed at 10.03–10.04 s in both step 15 sub-scenarios).
