**Verdict: closed for the core data-safety promise; two commands in the brief's

`disable`, `mode`, `trust`, `untrust`, `doctor --fix` — see `step3.log`.)

`ocm list` / `ocm info` / `ocm search` report the same corruption instead of

The two gaps:

- `ocm init`: exit 0, `auto-sync loader already current`, registry untouched.
  With the loader file removed it **reinstalls the loader** (a write) still

  is byte-identical — but the brief's test says "every mutating command
  refuses with the named error and exit 1". → **F126**.
- `ocm loader uninstall`: exit 0, prints `removed auto-sync loader`, and
  **deletes registry.json** (`rmSync(OCM_DIR, recursive)` in
  `src/loader.ts:194`) — the file is not byte-identical afterwards. Deleting
  `ocm/` is this command's documented behaviour for valid registries too
  (round-2 F30 design note), so this is a spec-vs-brief mismatch more than a
  new harm — but the plan and brief 27 §1.6 both list it in the must-refuse
  set. → **F127**.

Observation (not filed): doctor on the corrupt registry also blames ocm's own
links with `no marketplace owns this link (orphaned by a loader uninstall?) —
ocm doctor --fix removes it` — the cause guess is wrong (no uninstall
happened; doctor simply cannot read ownership), and the `--fix` hint is untrue
in this state because `--fix` refuses (exit 1) on the corruption and removes
nothing. F80-adjacent wording.

## F126 — `ocm init` does not refuse on a corrupt registry (area: CLI, severity: low)

Test:        A1 / step 3
ocm version: 0.6.0      opencode: 1.18.31
XDG:         unset
Command:     `echo '{' > $H/.config/opencode/ocm/registry.json` (home with one
             marketplace); then `ocm init`; then `rm …/plugins/ocm-loader.js`
             and `ocm init` again
Expected:    brief 27 §1.6 lists `init` in the mutating-command set and §5's
             test says "every mutating command refuses with the named error
             and exit 1, and the file is byte-identical afterwards"
Actual:      run 1: exit 0, stdout `auto-sync loader already current`, no
             error, registry byte-identical (md5 f95b70fd…).
             run 2 (loader removed): exit 0, stdout
             `installed auto-sync loader (/tmp/…/plugins/ocm-loader.js)` —
             a write performed against the corrupt registry, still no refusal.
             Registry remains byte-identical in both runs.
Impact:      no data loss (the registry is never touched), but the guard the
             brief specifies does not cover `init`; a user poking at a corrupt
             home gets a green command instead of the diagnosis every other
             mutating command gives.
Regression?: round 3 did not test `init` against corruption (F86 tested
             `update` only) — gap in coverage, not a regression.

## F127 — `ocm loader uninstall` deletes a corrupt registry instead of refusing (area: CLI, severity: low)

Test:        A1 / step 3
ocm version: 0.6.0      opencode: 1.18.31
XDG:         unset
Command:     `echo '{' > …/registry.json; ocm loader uninstall`
Expected:    brief 27 §1.6 includes `loader uninstall` in the mutating set;
             §5's test asserts the file is byte-identical after every
             mutating command
Actual:      exit 0, stdout `removed auto-sync loader`; afterwards
             `registry.json` no longer exists (md5 check: "No such file or
             directory"). `uninstallLoader` (`src/loader.ts:190-196`) does
             `rmSync(OCM_DIR, { recursive: true, force: true })` without ever
             loading the registry, so the corruption guard cannot fire.
Impact:      limited: deleting `ocm/` is this command's documented behaviour
             for valid registries too (round-2 F30 design note), and a user
             running `loader uninstall` has asked to remove ocm's machinery.
             But the output does not say the marketplace records went with
             it, and the brief/plan explicitly promise a refusal here.
Regression?: not a regression (round 3 never ran `loader uninstall` against
             corruption); a brief-27 promise that did not land for this
             command.

## F128 — local fold appearing at update leaves the skipped plugin's link cross-wired to the sibling's file; doctor green (area: CLI, severity: med)

Test:        A2 / step 7c
ocm version: 0.6.0      opencode: 1.18.31
XDG:         unset
Command:     local marketplace (on a case-sensitive volume) with `plain-kit` +
             `case-Kit`, `ocm add` (exit 0), then create `plugins/case-kit`
             and change `plain-kit` upstream, then `ocm update`
Expected:    brief 28 §3.3: "3b (both directories real): the folded pair's
             plugins are skipped with the warning, and the rest of the update
             proceeds" — with the F89 harm (a command link serving the other
             plugin's content) not surviving
Actual:      exit 0. The skip warning fires
             (`warning: plugins/case-Kit and plugins/case-kit differ only in
             case — plugin "case-kit" skipped; ask the author to rename one
             and update again`) plus the old cross-wire warning
             (`warning: case-kit:run.md conflicts with case-Kit:run.md`).
             Afterwards:
             - the registry holds only `plain-kit` (case-kit dropped), yet
               `~/.config/opencode/commands/case-kit:run.md` still exists and
               points at `…/plugins/case-Kit/commands/run.md` (content "run
               from case-Kit") — the exact F89 cross-wire, now serving a
               plugin that is no longer registered;
             - the update report says `0 created, 0 removed, 1 skipped` —
               "0 removed" while a registered plugin and its link did in fact
               go;
             - `ocm doctor`: exit 0, all green — the leftover link is outside
               the orphan sweep (F80 family).
Impact:      after an upstream rename-collision, opencode keeps executing a
             command from a plugin the registry no longer knows about, wired
             to the *other* plugin's file, with no verb but hand-editing to
             remove it, and doctor certifies the home clean.
Regression?: green in round 3? No — round 3's F89 was refused-at-add cross-
             wiring; the local-update path is new behaviour introduced by
             brief 28's skip rule, so this is a new defect in the fix, not a
             regression. (The git-source update path is correct: whole
             marketplace stops, previous revision stays materialized.)
