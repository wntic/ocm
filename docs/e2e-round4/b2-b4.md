## B2 — XDG behaviour

### Step 7 — PASS (`b2-7.log`, home-b24-7)
Add under `XDG_CONFIG_HOME=$H/xdg-a`, then unset, then re-set. Registry follows the env exactly; no split-brain; doctor's stranded report matches brief 28 §2.2 verbatim (names the stranded root, advises `unset XDG_CONFIG_HOME … or re-add`); `opencode debug config` agrees under each env (loader present only in the active root's plugin array).

### Step 8 — PASS + F186 (`b2-8.log`, home-b24-8)
`XDG_CONFIG_HOME=rel-xdg` (relative): registry lands at `<cwd>/rel-xdg/opencode/ocm/registry.json` — cwd-relative join, matching opencode itself. Root A byte-identical after operations from cwd B. Doctor from cwd B exits 1 with both the relative warning and the stranded-root error. opencode agrees from both cwds.

**F186 (low) — relative-XDG warning fires only in `doctor`, not at the `add` write boundary.** The warning text ("XDG_CONFIG_HOME is relative — every ocm command run from a different directory sees a different install") is exactly right, but `ocm add` under a relative XDG writes the registry with no warning on stdout/stderr; the user learns of the hazard only if they later run `doctor` from a different cwd. Brief 28's mutation-notice pattern suggests the write boundary is where it belongs.

### Step 9 — PASS (`b2-9.log`, home-b24-9)
`XDG_CONFIG_HOME=""` behaves as unset: registry at `$H/.config/opencode/ocm/registry.json`, no stray cwd-relative `opencode/` dir, opencode with empty XDG sees the same loader/plugins as with XDG unset.

### Step 10 — PASS + F188 (`b2-10.log`, home-b24-10)
Root A (`xdg-a`) then root B (`xdg-b`), shared cache at `$H/.cache/ocm`:
- `add` under root B prints the 3-line stranded mutation notice before proceeding (brief 28 §2.3) — correct.
- Root A's registry byte-identical after root B's add — no migration, correct.
- Doctor under each env names the active root and the stranded root with actionable advice — correct.

**F188 (med) — doctor's orphan check is cache-global, not per-root; `--fix` from one root destroys another root's links.** With root B active, doctor flags root A's links in the shared cache:

```
error   /tmp/ocm-e2e4/home-b24-10/.cache/ocm/links/demo-marketplace/skills/demo-kit--code-review: no marketplace owns this link (orphaned by a loader uninstall?) — ocm doctor --fix removes it
error   /tmp/ocm-e2e4/home-b24-10/.cache/ocm/links/demo-marketplace/skills/release-kit--release-notes: no marketplace owns this link (orphaned by a loader uninstall?) — ocm doctor --fix removes it
```

Verified destructive: `ocm doctor --fix` from root B removed root A's `links/demo-marketplace/skills/*` and root A's `skills.paths` entry, after which root A reports `materialized component(s) missing`. The registry is per-root but the links namespace is per-cache; ownership is resolved against the *current* root's registry only. Same root cause as F189.

### Step 11 — FAIL (`b2-11.log`, `b2-11b.log`, home-b24-11 / home-b24-11b)

**F187 (high) — adding the same git marketplace under a second XDG root crashes with a raw `ENOTEMPTY`, leaks a stray clone, and retries with a misleading error.**

`ocm add https://github.com/wntic/ocm-e2e-alpha` under root B (already added as `gh-alpha` under root A, same shared cache):

```
ENOTEMPTY: directory not empty, rename '/tmp/ocm-e2e4/home-b24-11/.cache/ocm/marketplaces/wntic-ocm-e2e-alpha' -> '/tmp/ocm-e2e4/home-b24-11/.cache/ocm/marketplaces/gh-alpha'
```

- Root cause: the clone is placed under its repo-derived name then renamed to the declared marketplace name (`loader/source.js:141`, `renameSync`); the duplicate check only inspects the *current root's* registry, so a marketplace already cloned into the shared cache by another root is not detected, and the rename target already exists.
- The failed add leaves a stray clone at `marketplaces/wntic-ocm-e2e-alpha`.
- Retrying the same command fails with a **misleading** message: `cannot access https://github.com/wntic/ocm-e2e-alpha — the repository is private, unreachable, or the URL is wrong` (cloning into the leftover stray dir fails; cleanup then removes the stray, so a third attempt would loop back to ENOTEMPTY).
- Workaround verified: `--name gh-alpha-b` succeeds; two roots then coexist; `ocm remove gh-alpha` in root A does not touch root B (`gh-alpha-b` unaffected, doctor clean).
- Displaced-record fields: stayed null throughout — not meaningfully exercised by these scenarios.

**F189 (med) — `ocm remove` in one root silently breaks the same marketplace in another root (local marketplace, same name).** Two roots, each with `ocm add <local-mp>` (name `demo-marketplace`): both adds succeed and share `cache/links/demo-marketplace/skills/`. `ocm remove demo-marketplace` in root A deletes the *shared* links directory; root B is left with:

```
error   /tmp/ocm-e2e4/home-b24-11b/.cache/ocm/links/demo-marketplace/skills: orphaned ocm skills path — target is gone (ocm doctor --fix)
error   marketplace "demo-marketplace": 2 materialized component(s) missing (ocm update)
```

Recoverable: `ocm update` in root B re-creates the links (2 created, doctor clean after). Shared root cause with F188: cache links are namespaced per marketplace name across roots, while registry/ownership is per-root.

## B4 — manifest-gate blast radius

### Step 17 — PASS (`b4-17.log`, `seq51.txt` / `seq60.txt`, home-b24-17a/17b)

Pin to v1.0.0 moved revision 52c841c → 1d272a4 with correct plugin downgrade; trust on code-less gh-alpha says "ships no code; nothing to trust", exit 0.

### Step 18 — FAIL for local sources (`b4-18.log` + confirmation run; git variant `b4-18b.log` PASSES)

Setup: copy of local-mp with `release-kit`'s `plugin.json` description blanked to `""`, added under 0.5.1 (`--no-trust`), then observed under 0.6.0.

- Phase 2 (no upstream change): grandfather intact — release-kit still listed, links present, opencode sees both plugins. Correct.
- Phase 3 (upstream change): **the grandfather never ends.** Appending to `commands/ship.md` produced no per-plugin output at all. Stronger confirmation: editing `plugin.json` itself (blanking `version` too) — update *refreshed the record* (`release-kit   0.1.0 → `) yet kept the gate-failing plugin installed with links intact, exit 0.

**F190 (med) — the manifest gate's "grandfather until changed" never fires for local marketplaces; it is "grandfather forever".** Change detection is git-revision-based: `pluginFileChanges` returns an empty map unless `before`/`after` revisions exist (`src/commands/update-report.ts:47`), and `pullMarketplace` never sets them for local entries (`src/commands/update.ts:85-87` — local directories are reported and skipped). The loader sync path (`loader/sync.js` `refreshRecords`) likewise passes no `changed` set. Consequence: a plugin that would fail the 0.6.0 manifest gate stays installed indefinitely on local marketplaces, even as its manifest visibly changes — the report even prints the new (invalid) version while keeping it installed.

The git-backed equivalent of the same scenario (`b4-18b.log`, home-b24-18b, same tree committed to git and added via `file://`): **PASS exactly per brief 29 §3.** After one upstream commit:

```
release-kit   uninstalled — plugins/release-kit/plugin.json: "description" is required and must be non-empty — add one line about the plugin and re-run ocm add
```

with stderr warning "changed upstream and no longer passes the manifest gate — uninstalled … fix it and run ocm update to reinstall it". Sibling demo-kit unaffected; links and registry record removed; opencode's command list drops `release-kit:ship`; doctor clean. Exit 0 throughout.

### Step 19 — PASS (`b4-18b` homes, home-b24-19)
`ocm validate /Users/yegorvorobyev/projects/opencode-marketplace/template` under 0.6.0: exit 0, zero findings. Control on the `bad-mp` fixture: exit 1 with the dotfile-command error and schema warning — error detection works.

**F191 (low, adjacent) — `ocm validate` is blind to bad manifests in component-less plugin dirs.** The `bad-mp` fixture's `broken-json` (invalid JSON) and `empty-desc` (empty description) plugins ship only a `plugin.json` with no components; discovery skips component-less dirs (`loader/discovery.js` `discoverPlugins` returns before collecting them), so `validate` reports nothing for them. Confirmed in isolation (`work-b24/componentless-mp`):

- `ocm validate` → exit 0, zero findings (no mention of the invalid JSON or empty description)
- `ocm add` on the same tree → exit 1, "no plugins found in … expected plugins/<name>/{commands,agents,skills}/"

So `validate` says the tree is fine while `add` refuses it — the two disagree, and the manifest gate cannot fire on a manifest discovery never surfaces. Low impact: nothing invalid installs (add refuses), but a marketplace author running `validate` gets a false clean.

## Delegated to human

- **F187** needs a product decision: should a cross-root duplicate be a clean refusal naming the other root (like the registry-dup message), an implicit second clone under a suffixed name, or shared-clone accounting? The retry's misleading "repository is private, unreachable" message is wrong regardless of that choice.
- **F188/F189** share one root cause (per-cache links namespace vs per-root ownership). Whether to scope links per root (breaking the shared-cache design) or to make doctor/remove ownership-aware across roots is an architecture call, not a bug fix.
- **F190**: if local-marketplace gate re-check is wanted, the change signal must come from somewhere other than git revisions (e.g. manifest fingerprint recorded at add time). Brief 29's §3 wording ("changed upstream") arguably only ever promised git semantics — hence a decision, not an obvious defect.
- F186 and F191 are small polish items; no decision needed beyond prioritization.
