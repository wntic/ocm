## F1 — no-op update rewrites the registry file (mtime churn) (area: CLI, severity: low)
Test: 17.6
Command: `ocm update mech` twice with no upstream change; `stat` registry.json before/after
Expected: mtime does not change when nothing changed (plan: "no churn")
Actual:
```
before: 1789291246 Sep 13 14:20:46 2026
updating mech...
  already up to date
exit=0
after:  1789291250 Sep 13 14:20:50 2026
MTIME CHANGED
```
diff of registry before/after shows the ONLY content change is `lastSync.at`:
```
~  18  "at": "2026-09-13T09:20:50.003Z", → "at": "2026-09-13T09:20:52.514Z",
```
Impact: any watcher (or the auto-sync loader's own interval logic) sees churn on every run;
also violates the plan's explicit no-churn expectation. Possibly intentional for
sync-interval bookkeeping, but a timestamp-only write could be skipped.
Status: new

## F2 — `ocm update <plugin>@<mp>` is not plugin-scoped in either action or report (area: CLI, severity: low)
Test: 17.5
Command: `ocm update stable-kit@mech` after an upstream commit touching old-name
Expected (task wording): updates mech but reports only that plugin — "judge what it actually does"
Actual: updates the whole marketplace and reports OTHER plugins' changes:
```
updating mech...
  1aad7cd → 7f81115
  old-name
    ~ commands/old-name.md
```
Impact: matches help text ("one plugin's marketplace"), so it is honest — but the form is
then exactly equivalent to `ocm update mech`; the plugin qualifier adds nothing. Either
scope the report to the named plugin or drop the form from help.
Status: new (UX observation)

## F3 — trust block and blocked-warnings interleave mid-report on a trust change (area: CLI, severity: med)
Test: 17.7
Command: modify trusted hook.js upstream, push, `ocm update` (stdout+stderr captured both
separately and combined; stdin </dev/null so the prompt auto-declines)
Expected: report readable as a unit; trust interaction clearly separated
Actual (combined stream, ANSI stripped):
```
marketplace "mech" shipped code that changed since you trusted it:
  modified: plugins/stable-kit/plugin/hook.js
marketplace "mech" ships code that opencode will execute:
  ...
trust this marketplace to run code? [y/N/skip]
updating mech...
  warning: blocked (untrusted): stable-kit:hook.js not linked — run `ocm trust mech` to approve

    ~ plugin/hook.js

```
The stderr "warning: blocked" line lands BETWEEN the `updating mech...` header and its

same interleaving occurs after the answer. Exit code is 0 despite blocked components.
Impact: on a trust change the stdout report is chopped into fragments by stderr lines;
the revision transition is visually orphaned from its marketplace header.
Status: confirmed-known-#6

## F6 — auto-installed plugins get installedAt = marketplace addedAt, not the real time (area: CLI, severity: low)
Test: 18.6 (noticed via chain-c), isolated with a fresh plugin
Command: push new plugin `ts-probe`, `ocm update mech` (mode auto) at 09:24:37Z
Expected: installedAt ≈ time of the update that installed it
Actual:

## F10 — "one-time" cache warning repeats forever while untracked files exist, and "discarded" is false for them (area: CLI, severity: med)
Test: 21.3
Command: create untracked file in cache (`commands/junk.md`), `ocm update mech` twice
Expected: one-time warning; local edits discarded
Actual: warning on EVERY update:
```
warning: /tmp/.../marketplaces/mech has local changes; discarded (the cache is not an editing surface)
```
while junk.md survives every update (reset --hard does not remove untracked files).
Warning only stops after I deleted junk.md by hand.
Impact: the warning is not one-time (violates plan expectation); it claims "discarded"
while the condition that triggers it is never cleaned; untracked files accumulate forever
and can collide with future upstream paths.
Root cause: dirty check is `git status --porcelain` (includes untracked); the fix is
`reset --hard` (excludes them). Either `clean -fd` alongside, or restrict the check to
tracked changes.
Status: new
