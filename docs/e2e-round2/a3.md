## F1 — `ocm remove` after `--force` takeover loses the hand-written file's path, no restore, no mention (area: CLI, severity: high)

Test:        Suite 4 / Test 11, step 5
Command:     `ocm remove alpha` (after `ocm install alpha-kit --force` displaced `alpha-kit:greet.md`)
Expected:    "your original hand-written file (restored or left alone) must survive" — either the file is back at `commands/alpha-kit:greet.md` or ocm leaves it and tells you where it is.
Actual:      `commands/alpha-kit:greet.md` no longer exists. Output of remove:
             ```
             removed marketplace "alpha"
               alpha-kit: 1 agents, 1 commands, 1 skills removed
               alpha-skills: 1 skills removed
             ```
             No mention of the displaced file. The only copy is buried at
             `~/.cache/ocm/displaced/2026-09-13T09-17-49-933Z/tmp/ocm-e2e/homes/a3/.config/opencode/commands/alpha-kit:greet.md`
             (checksum matches the original — data not destroyed, but effectively lost to a user).
Impact:      A user who force-installed over their own file and later removed the marketplace silently loses their command from its path. The displaced path mirrors the absolute source path under a timestamp dir — nobody will find it unaided, and nothing ever points there again.
Root cause:  loader/links.js:35 `takeOver` moves the file to the displaced dir; `removeMarketplace` (loader/core.js) removes ocm-owned symlinks but has no mechanism to restore displaced originals.
Status:      new

## F2 — Colliding install reports false success; next update silently reverts it (area: CLI, severity: high)

Test:        Suite 4 / Test 12, step 5
Command:     `ocm install review-tools@collide` then `ocm update collide`
Expected:    Install either refuses (naming both marketplaces, like `ocm add` does) or succeeds and materializes collide's files. State changes must be reported.
Actual:      ```
             warning: review-tools:review.md conflicts with review-tools:review.md
             installed review-tools@collide (1 command)
             ```
             Exit 0, claims success. `commands/review-tools:review.md` still symlinks to big's clone — nothing was materialized. The warning is also self-referential ("conflicts with review-tools:review.md" — same name both sides, marketplaces not named). The subsequent `ocm update collide` printed only "already up to date" while silently flipping collide's review-tools back to enabled=false in the registry.
Impact:      The user believes they installed collide's version; they are running big's. The silent revert on the next update makes the tool untrustworthy — state changed with zero output.
Root cause:  loader/links.js:81 warning names plugin:component for both sides; install path (src/commands or loader/core) marks enabled=true without checking `collision` recorded at update time; update recomputes collision and disables.
Status:      confirmed-known-#1

## F9 — `ocm doctor --fix` deletes a link the user just trusted; registry left inconsistent after loader-sync + `ocm trust` (area: loader, severity: high)

Test:        Suite 5 / Test 16, step 5 (follow-up)
Command:     loader sync (OCM_SYNC_INTERVAL_MS=0 opencode run) pulled new `plugin/other.js` → trustPending → `ocm trust exec` (approved) → `ocm doctor` → `ocm doctor --fix`
Expected:    doctor clean; the trusted component's link is ocm-owned and stays.
Actual:      ```
             error   ~/.config/opencode/plugins/ocm--exec-kit--other.js: stray ocm file — no registry entry owns it
             1 error, 0 warnings            (exit 1)
             ```
             then `ocm doctor --fix`:
             ```
             fixed   ~/.config/opencode/plugins/ocm--exec-kit--other.js: removed
             ```
             The link `ocm trust exec` had just created was deleted. Registry after: `trust.components` still lists other.js (grant intact), per-plugin record still `plugin: ["notify.js"]`, trustPending still true — every layer disagrees with every other layer.
Impact:      The user approved new code, then a routine repair pass silently removed it while claiming to "fix". Worst-case: users learn to ignore doctor errors, or lose trusted functionality with no notice. Subsequent `ocm update` re-adds the record and doctor goes clean — the inconsistency is real but self-healing only if the user happens to update again.
Root cause:  loader/sync.js:138 materializes after pull but never refreshes the registry's per-plugin `components` records (only the CLI update/reconcile path does); `ocm trust` (src/commands/trust.ts:104) creates links from on-disk components without refreshing them either; doctor-links.ts:53 then sees a link no registry record owns.
Status:      new
